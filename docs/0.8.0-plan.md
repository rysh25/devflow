# DevFlow 0.8.0 の実装方針と完了条件

Claude Code プラグインとしての利用を保ち、ローカル設定、Claude レビュアー、起動引数での
レビュアー指定、Codex ホスト対応を実装します。共通の規則と各ホストの標準機能を使い、
独自の権限機構、会話の偽記録、スキーマ変換は追加しません。

## ホスト指定

ランナーの全実操作で --host claude / --host codex を必須にします。
セッションなしの status / doctor にも既定値を設けません。内部 API でも host は必須引数です。
これは0.7.xの手動CLI・外部スクリプトに対する破壊的変更です。更新時に呼び出し元へ --host を追加します。
--help と --version は argparse が操作前に処理するため、ホスト指定なしで使えます。
形式1・2のセッションを Claude とみなす既存データの判定は、実操作の既定値とは区別します。

| 入力 | 結果 |
| --- | --- |
| status / doctor、フロー別診断、フック、変更操作で --host なし | 引数エラー。記録を変更しない |
| --host claude / --host codex を明示 | 指定ホストの規則で処理する |
| --help / --version | ホスト指定なしで表示する |

## 共通スキーマと起動コマンド

両フローの review.schema.json 原本に draft-07 を宣言します。プロンプトと各 CLI に同じ定義を渡し、
回答の制約は DevFlow が検査します。Claude 専用の宣言の削除や書き換えは行いません。
この方針は利用者の「おすすめで進めて」で承認済みです。
最終仕様は両フローとも draft-07 です。Implement の draft 2020-12 宣言の失敗と、宣言だけを外した
比較試験は検証履歴として残し、採用仕様とは区別します。

Claude の主 result は回答の制御項目と structured_output を検査します。
集計情報の不備でレビュー回答を失敗させません。tokens の採用には、主resultが1つで、
トップレベルの usage が存在しオブジェクトであることを必要とします。空の usage={} も認めます。
usage 内の項目は集計にも追加の必須項目検査にも使いません。数値の採用元は modelUsage だけです。
modelUsage は空でないオブジェクトで、各モデルの inputTokens / outputTokens /
cacheCreationInputTokens / cacheReadInputTokens がすべて非負整数（boolを除く）の場合だけ合計します。
この条件を満たさない場合や複数resultの場合は tokens を unknown にし、不正値を0と推測しません。
子の init / result は activity へ数え、主回答の成否判定へ混ぜません。
Claudeのassistant内の未知ブロックもactivity.other_eventsへ種類別に数えます。
既知のtext / thinking / redacted_thinkingは未知扱いにせず、ツール呼び出しの件数にも加えません。

両ホストのフックとスキルは uv --no-cache run --offline --no-project --no-config
--no-python-downloads で同じランナーを起動します。配布検査、導入時の許可例、復旧例も揃えます。
依存のないランナーで uv のキャッシュへの書き込みを避けるためです。

## ローカル設定の明示コンテキスト

devflow.config.local.json は、深さと大文字小文字を問わずスナップショットの対象外です。
context_paths に明示された場合、既存の対象範囲の検査により、スナップショット取得時に
Requested context file is not in the captured scope で止めます。設定読込時の専用検査は置きません。
設定を読むだけの doctor は、このパスの実取得までは検証しません。

## 主会話の判定

各ホストの公開契約と実測で確認した情報を使い、規則をホスト連携に置きます。
Claude は対応版の agent_id で子を区別します。Codex は agent_id と記録済みルート入力の turn を使い、
根拠がなければ unknown とします。Claude に主会話を証明する独自機構は追加しません。
Codex の通常入力の出所は unknown とし、照合済みの質問ツールの実回答だけを人間の回答数へ加えます。

## 質問の整合性と原文の保存

承認候補と Codex の面接取得は同じ照合規則を使います。host・実セッション・tool IDと質問入力を一致させ、
Codex は turn も一致させます。質問ID・質問文・選択肢のどれかが違う場合、承認候補にはしません。
面接取得は不整合を CaptureError にし、異なる質問の結果を流用しません。
両ホストとも画面が埋める answers / annotations を入力比較から除き、モデルの質問部分を比較します。
事前入力された質問と結果はprefilledとして原文を保ち、人間の回答数・承認候補には加えません。
同じtool IDのPreToolUseを繰り返す場合は、画面を経由しない入力同士なので入力全体の一致を必要とします。

対応する PostToolUse があれば、未回答・失敗・取消・中断・未確認の結果も原文で残します。
ホストが状態を確定できない場合は unknown のままで、取消などの理由を推測しません。
PostToolUse がない取消試行は質問を未回答として保持し、存在しない結果は作りません。
各メッセージの source は tool / turn ID、hook_event_index、outcome を持ち、元イベントへ対応します。

coverage の質問・回答件数は Claude と同じく質問ツール1呼び出しを単位にします。
1呼び出しに複数の質問IDがあっても1件で、各IDと文字列配列の対応は回答本文にそのまま残します。
Codex の prefilled_questions は事前入力された呼び出し、unanswered_questions はそれ以外で実回答のない呼び出しです。

APIの項目順と各turnのフック記録順を保ち、取得時刻はその間への配置に使います。
新しい captured_at はミリ秒精度です。既存の秒精度、同じミリ秒、時計のずれなどで混在順が確定できない場合は
source.ordering_ambiguous を付けます。時刻だけで別turnの入力を追い越したり、ネイティブ項目を並べ替えたりしません。
anchorは次のnative項目の直前への挿入位置で、同じanchorのフック同士は記録順です。
native時刻が単調な場合、フックと同じミリ秒のnative項目はその左に置き、同時刻の不確かさをフラグで示します。
同じturnのnative時刻に逆転があれば、そのturnの全質問・回答にordering_ambiguousを付けます。
API順とフックの記録順は維持し、別turnの時計の逆転だけではフラグを付けません。

## 会話APIの診断と待ち時間

APIのタイムアウトは1呼び出し30秒で、全ページ合計30秒にはしません。
最大10,000ページ・1ページ100項目の上限を診断へ表示します。後始末の wait / close の失敗で元の取得エラーを隠しません。
実セッションを指定した plan doctor は初期化・ルートの識別・先頭1ページを調べ、面接より前に疎通失敗を報告します。
run指定時は、runの(owner_host, owner_session)と呼出元の(host, session)が一致するときだけ接続します。
別の所有者・セッション指定なしでは固定設定の診断に留め、conversation_api は checked=false、ready=null、理由付きです。
全体doctorとセッションなしの診断は静的なままです。先頭ページの成功を全ページや将来の seal の保証とはしません。
可視ユーザー発言のcontentは、実測したブロック配列だけを受け付けます。
文字列・オブジェクト・nullなどの未確認の形はCaptureErrorにし、推測して変換しません。
公開の `$devflow:doctor` スキルも全体doctorだけを実行し、APIへ暗黙に接続しません。
5操作の起動・待機の説明は references/codex-runner.md を参照し、Plan固有の面接手順をdoctorに混ぜません。

## 共通経路と記録の整合

主会話の判定は common/hosts/ 内で、同じホスト・実セッションの記録済みルートturnと照合します。
router は質問イベントと既存イベントを渡し、判定規則を持ちません。
status の事前入力件数も承認候補と同じ agent_scope=main の条件を使います。
未確定の回答は outcome=unknown を保ち、元ペイロードにない is_error を追加しません。
Codexの取得結果は可視レコードと未知・除外の種類別件数を返し、Planがcoverageへ引き継ぎます。
所属不明の質問も読み飛ばして数えます。

設定解決は load_workflow_config に一本化します。prepare_review は予約前に PreparedReview を作り、
run_review はそれと結果の検査関数だけを受け取ります。予約後の再準備や、同じ入力引数の二重渡しは行いません。
実行ファイル名・質問ツール名・スキルの探索場所もホスト連携が持ち、Planにはスキルのメタデータ検査を残します。

## リリースの判断

Claude と Codex に同じ完了条件を当てます。製品の入口から両ホストで次を実行し、記録を確認します。

- Plan は実際の人間の回答を取得し、面接の固定、レビュー、完了、正式プランの保存まで進める。
- Implement はそのプランから開始し、check と review の同じ呼び出しを完了まで待ち、完了報告まで進める。
- 使うのは導入文書にある標準設定と各ホストの標準承認だけとし、設定や権限を自動変更しない。
- 既定権限で成功した範囲と、利用者が承認した後に成功した範囲を分けて記録する。

Codex の default_mode_request_user_input は開発中の機能で、利用者が明示的に有効にします。
機能の状態と実行時確認の必要性を doctor と導入文書に示します。
この明示設定を許容したうえで、上記の製品試験の結果により0.8.0への同梱を判断します。
成立確認やレビュアー単体の試験だけで全フローを完了扱いにしません。

Codex で上記が成立しなければ、ローカル設定・Claude レビュアー・起動指定を0.8.0にし、
Codex、ホスト分離、run 形式10・セッション形式3は一緒に後続版へ送る案を第一候補として相談します。
分割する場合は形式9・2を維持し、0.7.3 run の継続を確認します。
現在は分割リリースを選んでいないため、形式9で0.7.3 runを継続する試験は適用対象にしません。
分割へ切り替える場合は、レビュー予約あり・なしの再開、復旧、レビュー、要約、承認の回帰試験をその版の必須条件にします。

全フロー確認の実施状況は [検証範囲](validation.md) に記録します。

2026-11-07に両ホストの4フローが completed まで通りました。Codex の check は通常の
workspace-write で成功し、review はコマンドごとの標準承認後に成功しました。
質問機能の明示的な有効化と、必要なコマンドへの標準承認を条件として、Codex を0.8.0に含める方針を維持します。
コミット・配布公開や、Windows / macOS の実機確認を完了したという意味ではありません。
