# プロジェクト設定例

必要な例を対象プロジェクトの`devflow.config.json`としてコピーし、**人間がコマンド・対象範囲・合否条件を確認した上で**調整してください。各例は `schema_version` と `implement` を含む完全な設定ファイルです。プラグインがこの例を勝手に採用したり、必要なパッケージをインストールしたりすることはありません。既存設定がある場合は上書きせず、必要なキーを統合してください。

## 最小構成

`devflow.minimal.json` は両フローの基本設定です。Plan の `grill_skill` は、モデルから直接呼び出せる外部 `grilling` を指定します。別の実際の呼び出し名を使う場合も、外部スキルに `disable-model-invocation: true` がないことを確認してください。DevFlow にこのスキルは同梱されません。

Implement の `checks: []` は自動合格ではなく、人間による変更後のコード版の実確認を必要とします。自動化したい場合は、以下の例を参考に実プロジェクトで利用可能なチェックを登録してください。

## Python

`devflow.python.json`は、既存のuvプロジェクトにpytestが設定・導入済みであることを前提とします。`pyproject.toml`を補足資料として含めます。`--offline`のため、必要なPythonや依存がなければ失敗します。プラグインが実行するPython 3.11以降と、対象プロジェクトが使うPythonの版は別です。

## Next.js

`devflow.nextjs.json`は、ローカルの`node_modules`にTypeScriptとVitestが導入済みの例です。Jest等を使うプロジェクトでは、そのテスト環境に置き換えてください。Next.jsがあるだけでVitestが使えるという意味ではありません。

Windowsの`npm.cmd`を直接起動しないよう、ネイティブ`node`と既存のJavaScriptエントリーポイントを引数配列で指定しています。依存の内部エントリーポイントが変わった場合は、人間が検証して更新してください。フレームワーク・ライブラリの将来バージョンに対する互換性は保証しません。

## Unity

`devflow.unity.json`は**対象範囲のひな型だけ**で、チェックコマンドは空です。Unity Editorの場所、ライセンス、Test Frameworkの版、EditMode/PlayModeの選択、実機でしか確認できない項目はプロジェクトに依存するため、架空のEditorパスを実行可能な設定として埋め込んでいません。

このまま使うと、変更後の各コード版について人間の実確認を求めます。自動化する場合は、プロジェクト側で用意したネイティブの検証ランナー、またはPython等の検証スクリプトを`checks[].argv`へ登録してください。

そのランナーには、Unity Editorを正しい絶対パスで起動すること、終了を待つこと、テスト結果XMLが今回の実行で生成されたことを確認すること、失敗・エラー・結果未生成・テスト0件を失敗にすることを推奨します。標準出力へテスト件数・結果を出せばレビューパケットにも残ります。終了コード0だけで未生成XMLや過去の成功結果を合格扱いしないでください。

UnityテストのCLIオプションは、導入しているTest Framework版の[公式ドキュメント](https://docs.unity3d.com/Packages/com.unity.test-framework@1.1/manual/reference-command-line.html)を参照してください。リンク先は1.1系の説明であり、利用中のパッケージ版の仕様確認を省略するものではありません。

この例のincludeは`Assets` / `Packages` / `ProjectSettings`です。ルートの別ソースやツールも変更する計画なら、必要な範囲を開始前に追加してください。シーン・Prefab・アセット等のバイナリ変更は、自動テキストレビューだけで合格にはしません。
