Read the [Codex runner contract](../../references/codex-runner.md) before executing this operation. Use its trusted hook context, invocation, waiting and record-handling rules.

The human explicitly invoked $devflow:implement PATH, optionally with --reviewer AGENT MODEL EFFORT ... and --max-reviews N, then -- before PATH. The hook saved a pending start. Run implement doctor to inspect that pending input, then implement start --plan EXACT_PATH (and optional --workspace only when appropriate). Each workspace holds at most one unfinished implementation run; to work beside another implementation run, use a different worktree created outside the project or in a Git-ignored directory, with this conversation started at the project root and the worktree passed with --workspace. When Devin is a reviewer, it runs only in a directory it trusts or below one; a worktree under a directory Devin already trusts (for example a Git-ignored directory inside the project) shares that trust. `start` checks each reviewer in the workspace, and when Devin does not trust it, `start` refuses and creates no run. Then stop and tell the human to start `devin` once in the directory the error names (or a directory above it), trust it, and type the same `$devflow:implement` with the same arguments again: an ordinary message discards the pending start, so never retry `start` alone after one. When the human types the command again, call `start` with the same workspace as the refused start (the same `--workspace` value for a separate worktree). The trust result of `implement doctor` without a run applies only to the `reviewer_cwd` it reports (the project). A missing or unsupported reviewer CLI still blocks the start; a Devin refusal of the project blocks it only when the project will be the workspace, and when another worktree will be the workspace, that worktree's `start` result decides. Never skip the trust check. Settings are resolved and frozen by start; if it fails for another reason, fix the reported prerequisite and retry the same start before another ordinary input discards it.

Read the bundled references/implement-workflow.md beside the runner's scripts directory and follow its state loop. Preserve existing changes, modify only the frozen plan's scope in the recorded workspace, checkpoint, check, then review and reflect. Do not edit the input plan, any shared or local DevFlow project setting (common or host-specific), or run records. A passed ad hoc test does not replace the runner's check. Keep requested scope changes and human decisions explicit. At the limit, follow the returned runner state — an eligible run ends `auto_accepted` and a full-impossible round ends `exhausted` without a question. Only when the runner returns `awaiting_human` with a pending `review_budget` escalation, ask the review limit question as step 5 of references/implement-workflow.md says, and resolve only a recorded candidate. Never run human-only recovery yourself. Terminal reports describe recorded code; distinguish completed, accepted, auto_accepted, exhausted and failed checks.
