# Implement workflow

Use the runner from the invoking skill. All paths below refer to the current run directory returned by `status`; The host writes runner input files in `draft/`, and the runner writes the other, immutable records. Always inspect action JSON for its status: a zero process exit alone is not workflow completion.

## Loop

On Codex, start check/review once with exec_command and poll its returned session_id using write_stdin until completion; never replay the call. On Devin, run check/review once with exec, passing `bash_timeout_ms.check` or `bash_timeout_ms.review` as its timeout, and when it moves to the background wait with get_output on the returned shell ID until it completes; never rerun the call (see references/devin-runner.md). Standard permission approval must be explicit. On Claude Code, for `check` and `review`, pass `bash_timeout_ms.check` or `bash_timeout_ms.review` from the last runner result as the tool's timeout, unchanged; never lower it. If it is larger than the tool's maximum for foreground commands, run the call with `run_in_background: true` and that same timeout. When `bash_timeout_ms` has no `review` value (at the review limit), call `review` with the normal Bash timeout: it starts no reviewer. When a call runs in the background (yours, or one Claude Code moved there at its limit), wait for its completion notice and read the runner's JSON from the command's output; until then, do not change the workspace or start another runner action.

1. **implementing**: implement the frozen plan in the run's workspace (`workspace` in the DevFlow status context; the project unless `--workspace` was given). DevFlow does not limit tools; they follow the host's permission settings and the current mode. You may run tests and builds while working, but only `check` results count as validation. If the runner path changed after a plugin update, use the `runner` path from the DevFlow status context. Keep existing user changes. Implement the plan with the simplest code that meets it, following the project's conventions and the standard way of its language and libraries; keep each piece of knowledge in one place. Add generality, a setting, an extension point or an optimization only when the plan requires it or a foreseeable change needs it, and do not choose a clearly wasteful way of doing something: the Design balance section of `scripts/devflow_core/common/reviewer-rules.md` in the plugin directory (the directory that holds the runner's `scripts/` directory; read only that section) defines what counts as a foreseeable change, the standard alternatives and when an inefficiency is a defect, and the code must have none of the defects it describes. Check the frozen plan against the current code, its dependencies and the working environment before relying on what it assumes. Add and update only the code, documents and tests needed to implement or
verify the approved plan — project tests where appropriate — reusing what existing coverage already verifies, and verify with the rigor the required checks and the regression risk call for. Finish the work the frozen plan covers in this run: when a concrete constraint — an unresolved dependency, missing permission or a migration order that keeps compatibility — prevents a part of it, record the reason and its impact in the implementation summary, and escalate a change to the approved scope or conditions instead of narrowing it silently; work moved on your own judgment to a new plan, a pull request or a later run does not count as completed. Write `draft/implementation.md` with completed plan items, changed paths, test expectations, limitations, and any remaining work. Then `checkpoint --summary-file DRAFT_PATH`.
2. **ready_check**: call `check`, with its timeout as above. This executes the configured commands as argv (not arbitrary shell). If checks fail, inspect the saved output and fix within scope. A check that changes scoped source invalidates its snapshot and pauses the run; do not call that a pass.
3. **ready_review**: When no review has run since the human answered continue to the last review limit question or the run's `review_limit_auto` setting continued automatically (also after a resume or after answering a later escalation), first ask any unresolved issue that needs a human decision and make sure the changes the recorded answers call for are checkpointed and checked, as the review limit paragraph of the Recommendations to the human section says. Call `review` once, with its timeout as above. The runner chooses the next configured reviewer, reserves one attempt within the review limit, writes the packet (it names the diff file the checkpoint wrote), starts the reviewer in the workspace with the user's own CLI settings, and validates the result. The reviewer reads the code with its own tools. If the next status is still `ready_review`, continue with the next configured reviewer on the same snapshot; no gratuitous edits or repeated checks are needed. A reviewer whose execution failed — a timeout, a nonzero exit, or an answer that fails the checks — does not pause the run: the state stays `ready_review` and the next `review` request runs the next configured reviewer. When `review` returns `ready_review` with a non-null `last_error`, that round failed — tell the human its number, reviewer and error and that it used a review, in 1–2 lines, then call `review` again without waiting for the human. The run pauses (`paused_error`) only when the same reviewer also failed its own previous round (the saved error names the resume command), when the workspace changed during the review, or when the reviewer process may not have stopped completely (a child may still run); a process-cleanup failure pauses even at the review limit, where other failures return `ready_review` for the human budget question. When the run's frozen `review_limit_auto` is not `ask`, a cleanup failure while checking the workspace before or after a review also pauses at the limit; its `last_error` may carry the Git or workspace wrapper message, and the human must check for leftover processes before resuming. At the review limit (initially `max_reviews`: six by default, 1 to 99), `review` starts no reviewer: when one more review per configured reviewer fits within 99 reviews in total, it opens the review limit question (`awaiting_human`, question kind `review_budget`): continue, stop, or accept the current checkpoint; when adding them would pass 99 in total, it ends in `exhausted` without asking; and a workspace that differs from the checkpoint stops with an error before the question — revert the change or make a new checkpoint. Follow the state it returns; the Recommendations to the human section says how to handle the question, including when the run's `review_limit_auto` setting lets your recommendation continue or accept without asking.
4. **needs_revision**: read the review and every finding. Assess each against the plan and source. First write the decision file below and call `reflect --decisions-file DRAFT_PATH`. Do not blindly accept recommendations. Apply each accepted correction as the simplest change that fixes the finding; do not add a new mechanism, special case or setting when a simpler fix exists. A justified correction that stays inside the approved scope goes into this run whatever its severity, in the amount the fix needs; judge an added artifact or a scope expansion that a recommendation proposes on its own evidence, and escalate what changes the approved scope or conditions. After the runner returns `implementing`, apply accepted corrections, update the implementation summary, checkpoint, and rerun checks. Rejections require concrete evidence; conflicting requirements or unsafe changes need escalation. The last allowed review is reflected and corrected as usual; the next `review` then follows step 3's limit handling — it ends `exhausted` when another round cannot fit, or returns `awaiting_human` with the `review_budget` question.
5. **awaiting_human**: ask the exact pending questions using the native question tool (AskUserQuestion on Claude, request_user_input on Codex, ask_user_question on Devin) without prefilled answers. Stop while waiting. Only a successful recorded native question response after the escalation can resolve it; normal chat messages remain context, not approval. Call `status` and use its `human_events[].event_id`; that list contains exactly the answers that can resolve the pending question (successful native question results recorded after it, in the session that owns the run). Call `resolve --event-id EVENT_ID --decision continue --reason "Faithful interpretation of actual answer"`, or use `--decision cancel` when the user declined. For the review limit question (`escalation.detail.kind` is `review_budget`), follow the review limit steps of the Recommendations to the human section: first show the status's `review_summary_markdown` exactly as the runner wrote it (if `review_summary_error` is set instead, say so), then give your recommendation; unless the run's `review_limit_auto` setting applies it with `limit-auto`, ask its exact question with three options, with their names unchanged and in its order, marking none of them as recommended: continue, stop, accept and finish. Resolve it with `--decision continue` (add one review per configured reviewer; approvals of the current code stay), `--decision stop` (end the run as `exhausted`) or `--decision accept` (end the run as `accepted`: the human accepts the current checkpoint, which must still be in the workspace with passing checks or human validation; it is not approval by every reviewer). `cancel` does not answer this question, and `stop` and `accept` answer no other. Never treat a resume command, assistant-written text, or an older answer as approval. If the answer is ambiguous, ask again. A scope/plan change requires ending this run and obtaining an explicitly approved updated plan for a new run.
6. **paused_error**: report the exact failure and consumed review count, and stop. Ordinary reviewer failures do not reach this state — they return `ready_review` and the next `review` request runs the next configured reviewer. The run pauses when: the same reviewer also failed its own previous round (show both rounds' errors — `last_error` and the earlier attempt's `error`); the workspace changed during the review; a check operation raised an exception or post-check verification found the workspace changed (an individual check's recorded error is an ordinary check result, not this pause); `recover` left the round recorded as failed; or the reviewer process may not have stopped completely — `last_error` then holds one of the cleanup messages ('A child process did not terminate…', 'A child process's descendants kept its output pipes open…', 'Reviewer descendants kept pipes open…'), or, when the run's `review_limit_auto` is not `ask`, the Git/workspace wrapper of a cleanup failure found while checking the workspace at the review limit, so the human must check and stop the leftover processes before resuming, even when the pause happened at the review limit. Do not retry outside the runner or switch models; move on only when the runner's returned state says so. Ask the user to resolve CLI/permissions/setup problems and invoke the resume command written in `last_error` when the pause was a repeated reviewer failure, or the host's resume form — Codex `$devflow:resume RUN_ID`, other hosts `/devflow:resume RUN_ID` — for any other pause. A missing or unsupported reviewer CLI is detected before an attempt is reserved, so it does not consume a review.
7. **reviewing / checking**: if the call runs in the background, wait for its completion notice as above. If it is no longer running (for example, Claude Code was closed), a child process may still exist. Tell the human to inspect processes, then run the human-only `implement recover --confirm-process-stopped` from their own terminal. A result that arrives after cancel or recovery is kept under `late/` and never changes the run. Do not delete locks or call recovery yourself.
8. **completed / accepted / auto_accepted / exhausted / cancelled**: stop all source changes. A run is `accepted` only when the human chose to accept at the review limit; say so, and do not describe it as approved by every reviewer. A run is `auto_accepted` only when the run's `review_limit_auto` setting accepted the checkpoint at the limit following your recommendation; say so, and do not describe it as a human answer or as approval by every reviewer — its evidence is `limit-auto/ID-accept.json` and the summary's `auto_acceptance` (also in the saved report), and the accepted checkpoint may be unreviewed. A run is `exhausted` only when the human chose `stop` at the review limit, or when adding one round of reviewers would pass 99 reviews in total (98 with the default settings). First show the status's `review_summary_markdown` exactly as the runner wrote it. The summary already shows each review (its result, findings and tool calls), each reviewer's model, CLI and token counts, the failures, the remaining findings, the human decisions, the automatic decisions of the `review_limit_auto` setting, and whether the current version was reviewed and who approves it; do not repeat them. Then report only what it does not show: what was implemented, exact checks and results, and manual validation. Do not go on to push, publish or deploy unless the human explicitly asked for it or the project's rules say so. Completion is for the captured snapshot and is not a proof of correctness.

## Finding dispositions

Write this shape to `draft/decisions.json`; include exactly one entry for every finding ID from the latest review, and write each `reason` as the Recommendations to the human section says (for `escalate`, the runner asks the human the `reason` as the question, so write it as a question that follows the escalation guidance below). Allowed actions: `accept`, `reject`, `already_addressed`, `escalate`. If a review contains only human questions and no findings, use an empty decisions array after the human resolution.

```json
{
  "review_number": 1,
  "summary": "Assessed the findings against the frozen plan and current source.",
  "decisions": [
    {
      "finding_id": "F1",
      "action": "accept",
      "reason": "The null input path lacks the validation required by plan section 3 and no existing test reaches it; add the missing validation and a regression test. Design balance: one check in the existing validator, no new mechanism. Feasibility and efficiency: the validator already runs once per input. Convention: matches the existing checks."
    }
  ]
}
```

## Recommendations to the human

When you recommend an option to the human (an escalation question, whether you write it or the runner did; recommend only among the options it offers, and ask one without options as it is, with the native question tool as before and without a recommendation; a neutral entry that the tool needs only to show its free-text field is not an option and gets no recommendation, and a question whose response holds only that entry has no answer yet, so ask it again) or decide whether to accept a review finding, first read the Design balance section of `scripts/devflow_core/common/reviewer-rules.md` in the plugin directory (the directory that holds the runner's `scripts/` directory; read only that section — and, when the choice is whether to accept a review finding, the Recommendations section of the same file, which bounds the fix to recommend), then state how your choice fares on each of three points: the balance between a consistent design with the generality and extensibility a real need calls for and over-engineering, as that section defines it; feasibility (the APIs, hooks and CLI features it relies on exist, and the conditions it depends on, such as the state of the files, hold) and efficiency, as that section defines it; and whether it is the conventional way of the project and of its language and libraries. Write it in the question text of a question you write, in your message just before a pending question the runner wrote (ask that question's text unchanged), or in a finding's `reason` next to the concrete evidence the reason already needs, and if some point could not be verified in the actual code or documents, say so, naming only those points, not everything you checked. The message is its visible text, written before you call the native question tool: text that stays in your reasoning is not shown to the human, so write the recommendation there, and for the review limit question also the review summary before it. If your recommendation would go against a human decision, ask the human instead of recommending it.

The review limit question (`review_budget`) is the exception to the three points: do not read that section for it. Judge it only from these records and the review records they point to: when the summary lacks a detail you need, such as a finding's evidence for item 2, read the review's record (`record` in `reviews`). While the question waits, `status` shows `review_summary`: the severity and disposition (`action`: accept, reject or already_addressed; none means undecided) of each remaining finding, whether the current checkpoint was reviewed (`approval`) and which reviewers approve it, each review's number, reviewer, status and snapshot (`reviews`, whose `version.id` is the snapshot it saw and whose `error` holds a failed review's error), and the severity counts of the succeeded reviews (`finding_trend`; a failed review has none); and it shows whether the current checkpoint has passing checks or human validation (`validation`). The human decisions are the frozen plan and the answers in `human_decisions`. Only a succeeded review is evidence about the code: a failed one (a timeout, an answer that could not be parsed or broke the schema, no final answer) gave neither findings nor an approval.

The criterion follows the severities defined in the What to report section of `scripts/devflow_core/common/reviewer-rules.md`: accepting means the human takes the current checkpoint as usable as it is, a critical or high finding means the result cannot be used as intended or would cause harm, and a medium or low one does not stop its main use, so accepting needs the records to show that no serious issue remains. A serious issue remains when any of three conditions holds.

- First, a critical or high finding of the latest reviews is undecided.
- Second, a critical or high finding of any review in `reviews` (not only a remaining finding) was accepted and the records do not show that a later succeeded review saw a snapshot holding its fix: the review's `fix.file_changes` include the files you changed for that fix, and a later succeeded review saw the next reviewed snapshot or a newer one (a different snapshot alone is not enough, because an accepted finding can be checkpointed again unchanged or with only other files changed, and a review that saw the same snapshot as that review does not count); when the records cannot show it, count the fix as unreviewed and say what you could not verify; for these two conditions, findings rejected or found already addressed with evidence do not count.
- Third, a configured reviewer's latest succeeded review has a critical or high finding, whatever its disposition: `review_summary.serious_findings.reviewers` names each such reviewer and that review's number. A reviewer in `serious_findings.never_succeeded` is not counted for this condition; when there is one, say in your recommendation that that reviewer has never succeeded in this run.

An issue that needs a human decision is unresolved when no answer in the frozen plan or `human_decisions` settles it. Accepting is eligible when the records show that no serious issue remains, at least one review succeeded, no issue that needs a human decision is unresolved, and the current checkpoint has passing checks or human validation. Decide in this order:

1. When `limit_auto_decisions_error` is set, stop as the review_limit_auto paragraph below says: give no recommendation and do not ask the question, even when `review_summary_error` is set too, and also when it appears on a later `status` read (such as after a refused `limit-auto` in step 3 there). The rest of this item applies only when `limit_auto_decisions_error` is not set. When `review_summary_error` is set instead of the summary, give no recommendation: say so and ask the question as it is. When the error says a record changed or is missing (such as `Immutable artifact changed or is missing`), also say that the run's records must be examined first, because `resolve` verifies the records before it records an answer, so no option can be recorded until then. Likewise, when `status` itself fails while the question waits and reports a missing, unreadable or changed record, or when it sets `events_error` (the human event records cannot be read), give no recommendation, show the pending question only if you can read it exactly, and say that the run's records must be examined first, because no answer can be recorded until they verify.
2. Recommend stop only when accepting is not eligible and a premise is broken: evidence shows that an API, feature or condition that the frozen plan relies on does not hold, and fixing it needs a new, approved plan outside this run. When a human choice within this run settles it, item 3 applies instead.
3. Otherwise, when accepting is not eligible, recommend continue: a serious issue remains (whatever the finding counts do), no review has succeeded, the current checkpoint has neither passing checks nor human validation, or an issue that needs a human decision is unresolved.
4. Otherwise recommend accept. Remaining medium and low findings, however many and even when their number grows, are no reason to continue. Accepting also needs the workspace to still hold the checkpoint, which `status` does not show at the limit, so when you recommend accept, name that as a point you could not verify.

Failed reviews alone do not change this order, and item 2 still applies. When the same reviewer's latest attempts failed, recommend as above and add, as facts from the records, that reviewer and each failure's cause, whether the causes are the same or not; say that a cause lies in the run's frozen configuration (such as its `timeout_seconds`, the reviewer or the model), which cannot change within the run, only when the records support it. Whether to continue anyway is the human's decision. Apart from item 2, recommend continue for as long as a serious issue remains, however many times reviews were added; no number of rounds turns it into accept. The summary's remaining findings include findings already fixed in the current checkpoint, so judge them with their dispositions. Before you recommend, compare the recommendation with what the human stated about the number of reviews or how to end the run in the frozen plan and in the answers in `human_decisions` (`max_reviews`, `--max-reviews` and an earlier answer to continue are not such statements); if it would go against one, name that decision and the conflict and give no recommendation. A statement that the human decides at the review limit themselves (for example, at every limit) is such a statement for any recommendation: give no recommendation, so that the run's `review_limit_auto` setting does not act on one. When you give no recommendation, say why (`review_summary_error`, or the conflicting decision) and ask the question as it is. Name only the facts you relied on, without repeating the summary, and say that whether more reviews are worth their time and tokens is the human's decision, without weighing those costs.

The run's frozen `review_limit_auto` setting (`config.review_limit_auto` in `status`: `ask`, `continue` or `continue_accept`) decides whether your recommendation at the review limit may take effect without asking the human. Whenever `status` sets `limit_auto_decisions_error` instead of `limit_auto_decisions` — in any state, also on resume and right after a `limit-auto` call — an automatic decision record does not verify: stop, show the error to the human, and do not call `review` or `limit-auto` or ask the review limit question until the run's records are examined. When the review limit question is pending, follow these steps; steps 0, 2, 3 and 4 apply only when the setting is not `ask`. With `ask`, show the summary and your recommendation as step 1 says, then ask the question and `resolve` it as usual.

0. First check whether `status.human_events` holds a candidate (an answer recorded after the question). If it does, do not call `limit-auto` at this limit (the runner refuses it too): show the summary and your recommendation as step 1 says, say in one sentence that an answer recorded after the question prevents automatic progress, ask the review limit question with the native question tool as it is, and `resolve` it with the new answer. Never interpret a stored answer to use it for `resolve`.
1. Show the status's `review_summary_markdown` exactly as the runner wrote it (if `review_summary_error` is set instead, say so) and write your recommendation, in the visible text of a message you send before any `limit-auto` call, also when the setting will apply the recommendation automatically. The recommendation file of step 2 does not replace this message: the human sees only your messages.
2. When your recommendation is continue and the setting is `continue` or `continue_accept`, or your recommendation is accept and the setting is `continue_accept`: write the recommendation text exactly as you showed it to a file in `draft/` and call `limit-auto --escalation-id ESCALATION_ID --decision continue|accept --recommendation-file DRAFT_PATH`, with the status's `escalation.id` and your recommendation as the decision. The runner checks the mechanical conditions itself (among them, for continue, that the new limit stays within `review_limit_auto_extra_reviews` above `max_reviews`, and for accept, that a review succeeded, the workspace still holds the current checkpoint with passing checks or human validation, and no configured reviewer's latest succeeded review has a critical or high finding). When it succeeds, write one sentence in the visible text of your message, before any other runner call, saying that this run's `review_limit_auto` setting (name its value) continued automatically following the recommendation (limit X → Y), or accepted the checkpoint and ended the run, then continue from the returned state with the Loop. An automatic decision is recorded in `limit-auto/`, never as a human answer.
3. When the runner refuses, or the result is unknown (an error, or output you cannot read): make sure the call ended with the host's normal way of waiting (on Claude Code the foreground call's end or the background completion notice, on Codex `write_stdin`, on Devin `get_output`) before you read `status` again; never read it while the call may still run. When the runner reports that it cannot take the run lock (`Run is locked: …`), or the result is unknown and the run directory (`run_dir`) still holds `state.lock` (a process killed while holding it leaves the file, and `status` does not show it), stop before asking the question and do not delete the lock yourself: show the human the lock file's path and the `pid` and `host` it records, ask them to confirm that process has stopped and then move the lock file out of `.devflow` themselves (as with any stale DevFlow lock), and read `status` again after they say so. When `limit_auto_decisions` holds a record whose `escalation_id` is that question's ID, the automatic decision is final: report it and continue with the Loop. When the same question (the same `escalation.id`) is still pending, write one sentence in the visible text of your message, before you call the native question tool, saying why the runner refused (for example, the automatic continue limit was reached, or the acceptance checks failed), then ask the review limit question as it is. Otherwise (a human answer or a cancel closed the question, or another question is pending), continue from the current state with the Loop; never ask a closed question.
4. Otherwise, ask the human as usual and do not call `limit-auto`. Before the question, write one sentence in the visible text of your message saying why the run does not proceed automatically (for example: the recommendation is stop, there is no recommendation, the `continue` setting does not accept automatically, or a recommendation would go against a human decision). With `ask`, nothing changes and this sentence is not written.

After the human answers continue, or after the run's `review_limit_auto` setting continued automatically, the run returns to `ready_review`. Before the next `review`, ask every issue that needs a human decision and is still unresolved, whether or not your recommendation named it, with `escalate` (the Escalate an implementation decision section); with an automatic continue these questions still reach the human. This applies while no review has run since the last review limit question was answered continue, also after a resume or after answering one of these escalations: `status` lists the questions in `escalations` and the answers in `resolutions`; a question file `escalations/NNN.json` holds `detail.kind` (`review_budget`) and `detail.review_number`, and its answer in `resolutions/NNN.json` holds `escalation_id` and `decision` (`continue`); no review has run since when the number of `attempts` still equals that review number. After an automatic continue, the same holds while the last record in `limit_auto_decisions` whose `decision` is `continue` has a `review_number` equal to the number of `attempts` (`review_count`); when `status` sets `limit_auto_decisions_error` instead, stop before the review as the review_limit_auto paragraph above says. `status` shows no summary then, so read the review files in `attempts` (`review_path`), the files in `reflections` and the recorded answers as needed to find the unresolved issues. Do not ask again what a recorded answer already settles, but read the recorded answers and check that the changes they call for are in the workspace, the current checkpoint and `validation`; finish any missing in-scope change and its checks before the review. When an answer stays within the frozen plan and calls for a change, make it, then `checkpoint` and `check` before the review; when it keeps the current code, call `review` without a new checkpoint, because a checkpoint clears the current validation and needs the checks again. When an answer changes the plan or its approved scope, follow step 5: end this run and obtain an explicitly approved updated plan for a new run.

## Escalate an implementation decision

Write `draft/questions.json`, then call `escalate --questions-file DRAFT_PATH` before asking the user:

```json
{
  "reason": "The plan and existing public API impose conflicting requirements.",
  "questions": ["May the public API change, or must backward compatibility be preserved?"]
}
```

Escalate requirements changes, destructive operations, dependencies/new services/costs, security/privacy decisions, and other operations that need the human's authority. For conflicting reviewers, inaccessible tests and unexplained failures, isolate the cause with the frozen plan, the actual code, the saved logs and the safe checks available to you: escalate when completing the needed verification or continuing safely requires the human's judgment or authority; when the approved scope already resolves it, take the ordinary fix path. This triage never bypasses a failing required check or the runner's interruption and human-recovery procedures. Keep ordinary evidence-based code fixes automatic.

## Review coverage

The reviewer runs in the workspace and reads files with its own tools. The packet gives the original plan, the workspace path, branch and start commit, the list of changed paths (mode, size and hash before and after, no contents), the path of the checkpoint's `snapshots/NNN.diff` (every change in the snapshot scope since the run started), `snapshot.context_paths` as files to read first, the implementation summary, check results with their log paths, prior reviews/dispositions, and actual human decisions. Never silently trim an oversized packet. Binary changes require separate human inspection and are marked as such in the report. Files excluded/ignored by the frozen scope are not certified by this workflow, and a change a reviewer makes outside the snapshot scope is not detected.

## Human decisions

Prefer the native question tool without prefilled answers. Automated or inter-agent messages are not user approval. Do not run this workflow under a scheduler or mix automated messages into a human-decision session.
