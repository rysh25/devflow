# Implement workflow

Use the runner from the invoking skill. All paths below refer to the current run directory returned by `status`; The host writes runner input files in `draft/`, and the runner writes the other, immutable records. Always inspect action JSON for its status: a zero process exit alone is not workflow completion.

## Loop

On Codex, start check/review once with exec_command and poll its returned session_id using write_stdin until completion; never replay the call. On Devin, run check/review once with exec, passing `bash_timeout_ms.check` or `bash_timeout_ms.review` as its timeout, and when it moves to the background wait with get_output on the returned shell ID until it completes; never rerun the call (see references/devin-runner.md). Standard permission approval must be explicit. On Claude Code, for `check` and `review`, pass `bash_timeout_ms.check` or `bash_timeout_ms.review` from the last runner result as the tool's timeout, unchanged; never lower it. If it is larger than the tool's maximum for foreground commands, run the call with `run_in_background: true` and that same timeout. When `bash_timeout_ms` has no `review` value (at the review limit), call `review` with the normal Bash timeout: it starts no reviewer. When a call runs in the background (yours, or one Claude Code moved there at its limit), wait for its completion notice and read the runner's JSON from the command's output; until then, do not change the workspace or start another runner action.

1. **implementing**: implement the frozen plan in the run's workspace (`workspace` in the DevFlow status context; the project unless `--workspace` was given). DevFlow does not limit tools; they follow the host's permission settings and the current mode. You may run tests and builds while working, but only `check` results count as validation. If the runner path changed after a plugin update, use the `runner` path from the DevFlow status context. Keep existing user changes. Implement the plan with the simplest code that meets it, following the project's conventions and the standard way of its language and libraries; keep each piece of knowledge in one place. Add generality, a setting, an extension point or an optimization only when the plan requires it or a foreseeable change needs it, and do not choose a clearly wasteful way of doing something: the Design balance section of `scripts/devflow_core/common/reviewer-rules.md` in the plugin directory (the directory that holds the runner's `scripts/` directory; read only that section) defines what counts as a foreseeable change, the standard alternatives and when an inefficiency is a defect, and the code must have none of the defects it describes. Add/adjust project tests where appropriate. Write `draft/implementation.md` with completed plan items, changed paths, test expectations, limitations, and any remaining work. Then `checkpoint --summary-file DRAFT_PATH`.
2. **ready_check**: call `check`, with its timeout as above. This executes the configured commands as argv (not arbitrary shell). If checks fail, inspect the saved output and fix within scope. A check that changes scoped source invalidates its snapshot and pauses the run; do not call that a pass.
3. **ready_review**: call `review` once, with its timeout as above. The runner chooses the next configured reviewer, reserves one attempt within the review limit, writes the packet (it names the diff file the checkpoint wrote), starts the reviewer in the workspace with the user's own CLI settings, and validates the result. The reviewer reads the code with its own tools. If the next status is still `ready_review`, continue with the next configured reviewer on the same snapshot; no gratuitous edits or repeated checks are needed. At the review limit (initially `max_reviews`: six by default, 1 to 99), `review` starts no reviewer and asks the human instead (`awaiting_human`, question kind `review_budget`): continue, stop, or accept the current checkpoint.
4. **needs_revision**: read the review and every finding. Assess each against the plan and source. First write the decision file below and call `reflect --decisions-file DRAFT_PATH`. Do not blindly accept recommendations. Apply each accepted correction as the simplest change that fixes the finding; do not add a new mechanism, special case or setting when a simpler fix exists. After the runner returns `implementing`, apply accepted corrections, update the implementation summary, checkpoint, and rerun checks. Rejections require concrete evidence; conflicting requirements or unsafe changes need escalation. The last allowed review is reflected and corrected as usual; the next `review` then asks the human whether to add reviews.
5. **awaiting_human**: ask the exact pending questions using the native question tool (AskUserQuestion on Claude, request_user_input on Codex, ask_user_question on Devin) without prefilled answers. Stop while waiting. Only a successful recorded native question response after the escalation can resolve it; normal chat messages remain context, not approval. Call `status` and use its `human_events[].event_id`; that list contains exactly the answers that can resolve the pending question (successful native question results recorded after it, in the session that owns the run). Call `resolve --event-id EVENT_ID --decision continue --reason "Faithful interpretation of actual answer"`, or use `--decision cancel` when the user declined. For the review limit question (`escalation.detail.kind` is `review_budget`), first show the status's `review_summary_markdown` exactly as the runner wrote it (if `review_summary_error` is set instead, say so), then give your recommendation as the Recommendations to the human section says, then ask its exact question with three options, with their names unchanged and in its order, marking none of them as recommended: continue, stop, accept and finish. Resolve it with `--decision continue` (add one review per configured reviewer; approvals of the current code stay), `--decision stop` (end the run as `exhausted`) or `--decision accept` (end the run as `accepted`: the human accepts the current checkpoint, which must still be in the workspace with passing checks or human validation; it is not approval by every reviewer). `cancel` does not answer this question, and `stop` and `accept` answer no other. Never treat a resume command, assistant-written text, or an older answer as approval. If the answer is ambiguous, ask again. A scope/plan change requires ending this run and obtaining an explicitly approved updated plan for a new run.
6. **paused_error**: report the exact failure and consumed review count, and stop. Do not automatically rerun failed model calls or switch models. Ask the user to resolve CLI/permissions/setup problems and invoke `/devflow:resume RUN_ID`. A missing or unsupported reviewer CLI is detected before an attempt is reserved, so it does not consume a review.
7. **reviewing / checking**: if the call runs in the background, wait for its completion notice as above. If it is no longer running (for example, Claude Code was closed), a child process may still exist. Tell the human to inspect processes, then run the human-only `implement recover --confirm-process-stopped` from their own terminal. A result that arrives after cancel or recovery is kept under `late/` and never changes the run. Do not delete locks or call recovery yourself.
8. **completed / accepted / exhausted / cancelled**: stop all source changes. A run is `accepted` only when the human chose to accept at the review limit; say so, and do not describe it as approved by every reviewer. A run is `exhausted` only when the human chose `stop` at the review limit, or when adding one round of reviewers would pass 99 reviews in total (98 with the default settings). First show the status's `review_summary_markdown` exactly as the runner wrote it. The summary already shows each review (its result, findings and tool calls), each reviewer's model, CLI and token counts, the failures, the remaining findings, the human decisions, and whether the current version was reviewed and who approves it; do not repeat them. Then report only what it does not show: what was implemented, exact checks and results, and manual validation. Do not go on to push, publish or deploy unless the human explicitly asked for it or the project's rules say so. Completion is for the captured snapshot and is not a proof of correctness.

## Finding dispositions

Write this shape to `draft/decisions.json`; include exactly one entry for every finding ID from the latest review, and write each `reason` as the Recommendations to the human section says (for `escalate`, the runner asks the human the `reason` as the question, so write it as a question that follows the escalation guidance below). Allowed actions: `accept`, `reject`, `already_addressed`, `escalate`. If a review contains only human questions and no findings, use an empty decisions array after the human resolution.

```json
{
  "review_number": 1,
  "summary": "Assessed the findings against the frozen plan and current source.",
  "decisions": [
    {
      "finding_id": "F1",
      "action": "accept",
      "reason": "The null input path lacks the validation required by plan section 3; add the missing validation and a regression test. Design balance: one check in the existing validator, no new mechanism. Feasibility and efficiency: the validator already runs once per input. Convention: matches the existing checks."
    }
  ]
}
```

## Recommendations to the human

When you recommend an option to the human (an escalation question, whether you write it or the runner did; recommend only among the options it offers, and ask one without options as it is, with the native question tool as before and without a recommendation; a neutral entry that the tool needs only to show its free-text field is not an option and gets no recommendation, and a question whose response holds only that entry has no answer yet, so ask it again) or decide whether to accept a review finding, first read the Design balance section of `scripts/devflow_core/common/reviewer-rules.md` in the plugin directory (the directory that holds the runner's `scripts/` directory; read only that section), then state how your choice fares on each of three points: the balance between a consistent design with the generality and extensibility a real need calls for and over-engineering, as that section defines it; feasibility (the APIs, hooks and CLI features it relies on exist, and the conditions it depends on, such as the state of the files, hold) and efficiency, as that section defines it; and whether it is the conventional way of the project and of its language and libraries. Write it in the question text of a question you write, in your message just before a pending question the runner wrote (ask that question's text unchanged), or in a finding's `reason` next to the concrete evidence the reason already needs, and if some point could not be verified in the actual code or documents, say so, naming only those points, not everything you checked. If your recommendation would go against a human decision, ask the human instead of recommending it.

The review limit question (`review_budget`) is the exception to the three points: do not read that section for it. Judge quality only from what `status` shows while the question waits: in `review_summary`, the severity and disposition (`action`: accept, reject or already_addressed; none means undecided) of each remaining finding, whether the current checkpoint was reviewed (`approval`) and which reviewers approve it, each review's number, status and snapshot (`reviews`, whose `version.id` is the snapshot it saw), and the severity counts of the succeeded reviews (`finding_trend`; a failed review has none); and whether the current checkpoint has passing checks or human validation (`validation`). A serious issue remains when a critical or high finding of the latest reviews is undecided, or a critical or high finding of any review in `reviews` (not only a remaining finding) was accepted and the records do not show that a later succeeded review saw a snapshot holding its fix: the review's `fix.file_changes` include the files you changed for that fix, and a later succeeded review saw the next reviewed snapshot or a newer one (a different snapshot alone is not enough, because an accepted finding can be checkpointed again unchanged or with only other files changed, and a review that saw the same snapshot as that review does not count); when the records cannot show it, count the fix as unreviewed and say what you could not verify; findings rejected or found already addressed with evidence do not count. The findings are falling when the latest succeeded review reports fewer findings, or fewer critical and high ones, than the succeeded review just before it; earlier reviews are not compared, and with fewer than two succeeded reviews the trend is unknown. When `review_summary_error` is set instead of the summary, give no recommendation. Otherwise, recommend stop when what remains needs a scope change or a human decision; otherwise, when a serious issue remains, recommend continue if the findings are falling and stop if they are not (the same finding returns, or reviewers ask for opposite changes), and give no recommendation if the trend is unknown; otherwise recommend accept, but only when at least one review succeeded and the current checkpoint has passing checks or human validation. The summary's remaining findings include findings already fixed in the current checkpoint, so judge them with their dispositions. Accepting also needs the workspace to still hold the checkpoint, which `status` does not show at the limit, so when you recommend accept, name that as a point you could not verify. Before you recommend, compare the recommendation with what the human stated about the number of reviews or how to end the run in the frozen plan and in the answers in `human_decisions` (`max_reviews`, `--max-reviews` and an earlier answer to continue are not such statements); if it would go against one, name that decision and the conflict and give no recommendation. When you give no recommendation, say why (the missing fact, such as no succeeded review, an unknown trend, checks that have not passed or `review_summary_error`, or the conflicting decision) and ask the question as it is. Name only the facts you relied on, without repeating the summary, and say that whether more reviews are worth their time and tokens is the human's decision, without weighing those costs.

## Escalate an implementation decision

Write `draft/questions.json`, then call `escalate --questions-file DRAFT_PATH` before asking the user:

```json
{
  "reason": "The plan and existing public API impose conflicting requirements.",
  "questions": ["May the public API change, or must backward compatibility be preserved?"]
}
```

Escalate requirements changes, destructive operations, dependencies/new services/costs, security/privacy decisions, conflicting reviewers, inaccessible tests, and unexplained failures. Keep ordinary evidence-based code fixes automatic.

## Review coverage

The reviewer runs in the workspace and reads files with its own tools. The packet gives the original plan, the workspace path, branch and start commit, the list of changed paths (mode, size and hash before and after, no contents), the path of the checkpoint's `snapshots/NNN.diff` (every change in the snapshot scope since the run started), `snapshot.context_paths` as files to read first, the implementation summary, check results with their log paths, prior reviews/dispositions, and actual human decisions. Never silently trim an oversized packet. Binary changes require separate human inspection and are marked as such in the report. Files excluded/ignored by the frozen scope are not certified by this workflow, and a change a reviewer makes outside the snapshot scope is not detected.

## Human decisions

Prefer the native question tool without prefilled answers. Automated or inter-agent messages are not user approval. Do not run this workflow under a scheduler or mix automated messages into a human-decision session.
