First read the Devin runner contract, `references/devin-runner.md` in the plugin (the directory above the hook context's `runner` script's `scripts/` directory). Follow it for the hook context, the runner command, waiting, approval and questions.

The human typed /devflow:implement PATH, optionally with `--reviewer AGENT MODEL EFFORT ...` and `--max-reviews N`, then `--` before PATH. The hook saved a pending start. Run `implement doctor` to see that pending input, then `implement start --plan EXACT_PATH`, adding `--workspace` only when another worktree suits the task. One workspace holds at most one unfinished implementation run; to work beside another one, use a different worktree (outside the project or in a Git-ignored directory) and pass it with `--workspace` while this conversation stays at the project root. When Devin is a reviewer, it runs only in a directory it trusts or below one; a worktree under a directory Devin already trusts (for example a Git-ignored directory inside the project) shares that trust. `start` checks each reviewer in the workspace, and when Devin does not trust it, `start` refuses and creates no run. Then stop and tell the human to start `devin` once in the directory the error names (or a directory above it), trust it, and type the same `/devflow:implement` with the same arguments again: an ordinary message discards the pending start, so never retry `start` alone after one. When the human types the command again, call `start` with the same workspace as the refused start (the same `--workspace` value for a separate worktree). The trust result of `implement doctor` without a run applies only to the `reviewer_cwd` it reports (the project). A missing or unsupported reviewer CLI still blocks the start; a Devin refusal of the project blocks it only when the project will be the workspace, and when another worktree will be the workspace, that worktree's `start` result decides. Never skip the trust check. Start freezes the settings; if it fails for another reason, fix the reported prerequisite and run the same start again before another ordinary input discards it.

Read `references/implement-workflow.md` beside the contract and follow its state loop: implement only the frozen plan in the recorded workspace, keep existing changes, checkpoint, check, review and reflect. Do not edit the input plan, `devflow.config.json`, `devflow.config.local.json` or run records. Only the runner's `check` counts as validation. Run `check` and `review` once each with exec and wait with get_output as the contract says. When a human decision is needed, ask with ask_user_question. At the review limit, ask the review limit question as step 5 of `references/implement-workflow.md` says, and resolve only with a recorded answer. Never run the human-only `recover` yourself. In the final report, tell completed, accepted, auto_accepted, exhausted and failed checks apart.
